# 開発計画

# 概要
- ゲーム仕様は Game_Rule.md を正とする。本書は、その仕様を Claude Code と Godot で実装するための手順と方針を定める
- 対象：スマホ向け縦画面（まず Android で実機確認。iOS は Mac 環境が必要なため後回し）
- エンジン：Godot 4系の最新安定版、言語は GDScript（静的型付けを使う）
- 進め方：小さなフェーズに分け、各フェーズの「完了条件」を満たしてから次へ進む
- 最初の目標（MVP）：主人公1人・ダンジョン1つで、タイトルからクリアまたはゲームオーバーまで1周遊べる状態

# 開発の基本方針

## 1. ロジックとUIを分ける
- バトルのルール（ターンの流れ、ダメージ計算、デッキ処理など）は、画面に依存しないスクリプトとして実装する
- UIはロジックの状態を表示し、プレイヤーの操作をロジックに伝えるだけにする
- ロジックはシグナル（イベント）で変化をUIに通知し、UIはそれを受けて演出する
- これにより、ロジックを画面なしで自動テストでき、Claude Code が自分で動作確認しやすくなる

## 2. データ駆動
- カード、主人公、仲間、敵、装備、イベント、ダンジョンは、Godot のカスタムリソース（.tres）で定義する
- データの型（項目と入力範囲）は GDScript のリソースクラスで定義し、Godot のインスペクターで入力フォームとして編集できるようにする
    - 種別・レアリティなどの選択肢は列挙型（enum）にして、プルダウンで選べるようにする
    - 数値は入力範囲を設定し、範囲外の値を入れられないようにする
    - 召喚する仲間や初期デッキのカードなど、他のデータは直接参照で指定する
- カードの効果は「効果の部品」の組み合わせで表す（例：ダメージ、アーマー付与、回復、ドロー、パラメーター変更、召喚）
- カードや敵の追加は、原則としてデータの追加だけで済むようにする
- 未確定の数値（初期デッキ、出現確率、回復量など）もデータまたは設定ファイルに置き、コードに直接書かない

## 3. 乱数はシード付きで管理する
- 1回の挑戦（ラン）ごとにシード値を持つ乱数生成器を使う
- 同じシードなら同じ結果になるようにし、テストやバグの再現、セーブからの再開に使う

## 4. 仮素材で先に完成させる
- イラストは、最初は色付きの四角形と文字で代用する
- ゲームが1周遊べるようになってから、イラスト（ローカル生成など）、エフェクト、サウンドに差し替える

## 5. 小さく作って毎回動かす
- 1つの作業ごとに、テストが通る・起動できる状態を保つ
- コミットは指示した時だけ行う。区切りの良いところ（作業やフェーズの完了時）で、コミットを依頼する

## 6. ローカライズを前提にする
- 現在の対応言語は日本語。将来、英語などを追加しやすい形で作る
- 画面に表示する文章は、Godot の翻訳機能を使い、翻訳ファイル（CSV）に「キー」と「文章」で登録する
    - スクリプトや .tres には文章を書かず、キーだけを持たせる
    - 言語の追加は、翻訳ファイルに言語の列を足すだけで済むようにする
- 翻訳ファイルは種類ごとに分ける（UI、カード、キャラクター、イベントなど）。表計算ソフトで編集でき、UTF-8 で保存する
- 数値を含む文章は、差し込み用の目印を使う（例：「{damage}のダメージを与える」）。カードの数値をインスペクターで変えると、説明文の数値も自動で変わる
- 文字を画像に描き込まない。文章の長さが言語で変わっても崩れないよう、折り返しや自動縮小を使う
- 日本語を表示できるフォントを同梱する

# 実装上の前提（Game_Rule.md の補足仕様の扱い）
Game_Rule.md の「補足仕様」はすべて確定仕様として扱う。実装するフェーズは次のとおり。

| 項目 | 実装フェーズ |
|---|---|
| 全N戦のNの定義（Nの値はデータで設定） | フェーズ4 |
| ダメージ処理の順序 | フェーズ2 |
| ターゲット率による攻撃対象の決定 | フェーズ2 |
| イベントの例（サンプルデータとして使う） | フェーズ4 |
| ゲーム要素のアンロック | フェーズ5 |
| 中断とセーブ | フェーズ6 |

未確定事項（状態効果の種類、初期デッキ、各種数値、戦闘数）は、サンプルデータで仮置きし、後から差し替える。

# データ形式の例
実際の項目は Game_Rule.md のパラメーター定義に合わせて、フェーズ1で確定する。

## カード（リソースの型定義）
```gdscript
class_name CardData
extends Resource

@export var id: StringName
@export var name_key: StringName                 # カード名のキー（例：CARD_FIREBALL_NAME）
@export var card_type: GameEnums.CardType        # 召喚・攻撃・付与・空間
@export var rarity: GameEnums.Rarity             # コモン〜レジェンド
@export var usable_heroes: Array[StringName]     # 利用キャラクター（主人公のID）
@export var targets: Array[GameEnums.Target]     # ターゲット（複数可）
@export_range(0, 99) var cost_mana: int

@export_group("必要触媒")
@export_range(0, 99) var required_red: int
@export_range(0, 99) var required_blue: int
@export_range(0, 99) var required_green: int

@export_group("効果")
@export var duration: GameEnums.Duration         # 瞬間・〇〇ターン・バトル中・永続
@export_range(0, 99) var duration_turns: int     # 「〇〇ターン」の場合のターン数
@export var effects: Array[EffectData]           # 効果の部品
@export var description_key: StringName          # 効果詳細のキー（例：CARD_FIREBALL_DESC）
@export var visual_effect: StringName            # 効果エフェクト
```

## 効果の部品
- 効果の部品は EffectData を親クラスとし、種類ごとにサブクラスにする
- インスペクターで効果を追加する際、種類（ダメージ、アーマー付与など）を選ぶと、その種類に必要な項目だけが表示される

```gdscript
class_name DamageEffect
extends EffectData

@export_range(0, 9999) var amount: int
```

```gdscript
class_name SummonEffect
extends EffectData

@export var ally: AllyData    # 召喚する仲間を直接参照する
```

## 敵（リソースの型定義）
```gdscript
class_name EnemyData
extends Resource

@export var id: StringName
@export var name_key: StringName                 # 敵の名前のキー（例：ENEMY_SLIME_NAME）
@export_range(0, 9999) var max_hp: int
@export_range(0, 9999) var defense: int
@export_range(0, 9999) var armor: int
@export_range(0, 9999) var attack_min: int
@export_range(0, 9999) var attack_max: int
@export_range(0, 9999) var target_rate: int = 100
@export var race: GameEnums.Race
@export var attack_effect: GameEnums.AttackEffect
@export var pattern: Array[EnemyActionData]      # 行動パターン
```

## 翻訳ファイル（CSV）の例
```
keys,ja
CARD_FIREBALL_NAME,火球
CARD_FIREBALL_DESC,{damage}のダメージを与える
ENEMY_SLIME_NAME,スライム
UI_TURN_END,ターン終了
```
- 英語を追加する時は、en の列を足して英語の文章を入れる
- 説明文の {damage} には、カードの効果データ（DamageEffect の amount）の値が入る

## データ設計の注意点
- **循環参照を避ける**：主人公は初期デッキのカードを直接参照する。逆にカードから主人公を参照すると循環するため、カードの「利用キャラクター」は主人公のIDで持つ
- **列挙型はまとめて定義する**：種別、レアリティ、ターゲット、種族、攻撃エフェクトなどは GameEnums に集約する。列挙型の値の並び順を後から変えると既存データの値がずれるため、追加は末尾に行う
- **データの一覧**：全データを一覧にした索引リソース（data_index.tres）を、tools/ のスクリプトで自動生成する。ゲームはこの索引から読み込む（スマホ向けに書き出した後でも、フォルダを探索せずに確実に読み込めるようにするため）

# フェーズ計画

## フェーズ0：環境構築
- Godot と Git を準備し、プロジェクトを作成する
- 縦画面の設定を行う（基準解像度 720×1280、ストレッチモード canvas_items、アスペクト expand）
- フォルダ構成を作成し、docs に Game_Rule.md と本書を置く
- プロジェクト直下に CLAUDE.md を置く
- 翻訳の仕組みを準備する（localization/ に翻訳ファイルを作り、Godot に登録する）
- 日本語を表示できるフォントを同梱し、プロジェクト全体の標準フォントに設定する
- 自動テストの仕組み（GUT などのテストフレームワーク）を導入し、コマンドラインから画面なしでテストを実行できるようにする

**完了条件**
- 空のタイトル画面が縦画面で起動する
- タイトル画面の文字が、翻訳ファイルのキーから日本語で表示される
- サンプルのテストがコマンドラインで実行でき、成功する

## フェーズ1：データ定義と読み込み
- 列挙型（GameEnums）と、各データ（カード、効果の部品、主人公、仲間、敵、敵の行動、装備、イベント、ダンジョン）のリソースクラスを作る
- tools/ に次のスクリプトを作る（コマンドラインから画面なしで実行できるようにする）
    - サンプルデータの生成
    - 索引（data_index.tres）の自動生成
- データの読み込み処理と、検証処理を作る
    - インスペクターの入力制限では防げない誤りを検出する（IDの重複、攻撃力最少値が最大値を上回る、召喚効果に仲間が未設定、利用キャラクターに存在しない主人公のID、索引への登録漏れ、翻訳ファイルに存在しないキーなど）
- サンプルデータの文章は、すべて翻訳ファイルに登録する
- サンプルデータを用意する
    - 主人公：1人
    - カード：10枚程度（無色、赤、複数色、召喚魔法を含む）
    - 仲間：1〜2種類
    - 敵：通常の敵3種類、ボス1体（味方を呼ぶ行動を含む）

**完了条件**
- 全データが読み込め、検証でエラーが出ない
- 不正なデータを与えると、検証がエラーを報告するテストが通る
- Godot エディタのインスペクターで、サンプルのカードと敵を開いて編集できる（プルダウンや入力範囲が機能している）

## フェーズ2：バトルロジック（画面なし）
Game_Rule.md の「バトル中、ターンの流れ」13手順をそのまま実装する。

- バトル状態（主人公、仲間、敵本体、敵の仲間、デッキ、ゴミ箱、手札、マナ、魔法触媒）
- デッキ処理：バトル開始時のシャッフル、ドロー、デッキが空の時の再シャッフル
- マナのリセットと、魔法触媒の増加（1ターン目は増加しない）
- カード利用：消費マナの判定と消費、必要触媒の条件判定（消費しない）
- ダメージ処理：防御力、アーマー（ターンをまたいで残る）、HP
- 効果ターン数：効果を受けた側のターン終了時に1減らす
- 仲間：召喚、自動攻撃（召喚したターンから参加）、最大3体、上限時の入れ替え
- 敵：行動パターン（ループと条件分岐）、行動予告、味方を呼ぶ（敵の仲間が3体いる時は呼ばない）
- 攻撃対象：ターゲット率による抽選（攻撃の瞬間に抽選）
- 勝敗：敵本体を倒したらバトル終了、主人公が死んだらゲームオーバー
- 手札：ターンをまたいで残る、手番終了時に最大手札数を超えていたら捨てる

**完了条件**
- 次のテストがすべて通る
    - デッキが空の時にゴミ箱が再シャッフルされる／両方空の時はドローしない
    - 手札が次のターンに残る／手番終了時に超過分を捨てる
    - 1ターン目は魔法触媒が増加しない
    - 必要触媒を満たさないカードは使えない／使っても触媒が減らない
    - 「ターン開始時にマナ基準値+1」の効果がそのターンのマナに反映される
    - ダメージ処理の順序と、アーマーの持ち越し
    - カードで敵本体を倒した時点でバトルが終了する
    - 仲間が残っていても主人公の死亡でゲームオーバーになる
    - 仲間4体目の召喚で入れ替えが発生する
    - 敵の仲間が3体の時、敵は味方を呼ばない
    - 効果ターン数が正しく減り、0で効果が終わる
    - 同じシードで同じ結果になる
- コンソール上で、サンプルデータの1バトルを自動で最後まで進められる

## フェーズ3：バトル画面
Game_Rule.md の「画面レイアウト案」のバトル画面に従って作る。

- 各領域の配置（ヘッダー、敵エリア、味方エリア、ステータス帯、手札エリア、操作帯）
- カードの表示（カード名、種別、消費マナ、必要触媒、レアリティ、効果詳細）
- カードの操作：ドラッグで使用、対象の選択、キャンセル、タップで拡大
- 使えないカードを暗く表示する
- 敵の行動予告、状態効果の表示
- 手札超過時の捨てるカード選択、召喚上限時の入れ替え対象選択
- デッキとゴミ箱の中身の確認
- 最低限の演出（ダメージ数値の表示、攻撃時の小さな動き）
- 画面の文章はすべて翻訳ファイルのキーから表示する

**完了条件**
- サンプルデータで1バトルを画面操作で最後まで遊べる
- PC上で、縦画面の比率でレイアウトが崩れない
- 仮の英語列（キー名をそのまま入れたものなど）に切り替えても、レイアウトが崩れない

## フェーズ4：ラン進行（MVP完成）
- 現在のラン状態の管理（主人公、HP、最大HP、所持カード、装備、マップ、現在地、シード）
- 画面遷移：タイトル → ダンジョン選択 → 主人公選択 → マップ → 各ノード → 報酬 → マップ
- マップ：まず固定マップで流れを通し、その後ランダム生成（生成ルールは Game_Rule.md の「進路選択」に従う）
- ノード：通常戦、イベント、休憩、ボス
- 報酬：カード3択（スキップ可）
- 休憩：HP回復、カード削除、カードランダム交換（同じレアリティ）
- イベント：サンプル3種類
- バトル終了時の処理（HPのみ引き継ぎ、その他はリセット）
- ゲームオーバー画面、クリア画面、デッキ確認画面

**完了条件**
- タイトルから、クリアまたはゲームオーバーまで1周遊べる（＝MVP完成）
- 1周のプレイ時間を計測し、目標（数分〜30分）との差を確認する

## フェーズ5：ローグライク要素の拡張
- エリート戦、宝箱ノード
- 装備（指輪、武器、鎧）：同種1つまで、現在装備との差分表示、入れ替えまたは破棄
- レアリティ（コモン、アンコモン、レア、レジェンド）と出現確率、戦闘を重ねるほどレア率が上がる仕組み
- カード報酬のルール：利用キャラクターで絞る、種別の偏りを避ける、触媒色の重み付け
- ボス報酬：レア・レジェンドを含むカード3択、上級装備（レア以上）
- ゲーム要素のアンロック

**完了条件**
- 全ノード種類が出現し、報酬ルールがテストで確認できる

## フェーズ6：中断とセーブ
- マップ表示に戻るたびに自動保存する
- 「続きから」で再開する。バトル中の中断は、そのバトルの開始時点から再開する
- アンロック状況の保存

**完了条件**
- アプリを終了して再起動しても、最後の保存時点から再開できる

## フェーズ7：演出・アート・サウンド
- 仮素材を正式なイラストに差し替える（カード、キャラクター、背景、アイコン）
- カード使用時のエフェクト、仲間・敵の攻撃エフェクト（打撃、斬撃、刺突、炎・水・風魔法）
- 効果音、BGM、画面遷移の演出

**完了条件**
- 全画面で仮素材が残っていない

## フェーズ8：スマホ実機対応と調整
- Android 向けにビルドし、実機で動作確認する
- ノッチやジェスチャーバーを避けた表示（セーフエリア）、タップ領域の大きさ、文字の読みやすさを確認する
- 動作の重さ、電池消費を確認する
- データの拡充（主人公、カード、敵、イベント、ダンジョンの追加）とバランス調整
- 必要に応じて、設定画面に言語の切り替えを追加する

**完了条件**
- 実機で1周遊べ、操作上の不満点が解消されている

# Claude Code での進め方

## 依頼の単位
- 1回の依頼は「フェーズ内の1作業」程度に絞る（例：「フェーズ2のデッキ処理を実装し、テストを書いて通して」）
- 大きな作業は、先に計画（変更するファイルと手順）を出してもらい、確認してから実装させる
- 作業が終わったら、テスト結果と変更点の要約を報告させる

## 依頼文の例
```
docs/Game_Rule.md と docs/Dev_Plan.md を読んで、フェーズ2の「デッキ処理」を実装してください。
- scripts/core/ に実装し、UIには依存させないこと
- Game_Rule.md の「概要」と「ターンの流れ」5番の仕様に従うこと
- tests/ にテストを書き、コマンドラインで実行して全て通ることを確認すること
- 仕様が不明な点は推測で実装せず、質問してください
```

## 確認の仕方
- ロジックは、Claude Code にテストを実行させて確認する
- 画面は、自分で Godot エディタから起動して触って確認する
- 不具合は「再現手順」「期待した動き」「実際の動き」をセットで伝える

# CLAUDE.md
- プロジェクト直下の CLAUDE.md に、Claude Code の作業ルール（コーディング規約、データとテキストの扱い、進め方）をまとめている。Claude Code は作業のたびにこれを読む
- テストの実行コマンドはフェーズ0で、データ索引の再生成コマンドはフェーズ1で確定し、CLAUDE.md の「よく使うコマンド」に追記する
